# План перехода на Rust (полный переход)

Цель: Rust‑пайплайн должен повторять JS‑пайплайн по структуре/обязательным полям XML. Случайные поля (Title/Description/Price и т.п.) не обязаны совпадать 1‑в‑1.

## Текущий статус (сводка)

1. Каркас — готово
   - Workspace `rust/`, `crates/feed-core`, `crates/feed-cli`.

2. Доменные модели / ввод данных / валидации — готово
   - Модели: `Plan`, `Task`, `PublicationSlot`, `Location` (с `percent`/`addr`), `Aliases`, `UpdateRules`, `Ad`, `PhotoMapping`.
   - Константы: `MATERIAL_ALIASES`, `CITY_ALIASES`, `TOP_5_TITLES`, `EXACT_TITLES`.
   - Конфиг окон/шага: `config/feed.json`, загрузчик `FeedConfig`.
   - Чтение: `read_plan`, `read_update_rules`, `read_ads_from_excel`.
   - Валидации плана: counts/окна/шаги/парсинг дат.

3. Обновление старых объявлений — работает
   - `update_old_ads.json` поддержан (byLists/byId/updateAll).
   - Нормализация address по алиасам.
   - Для услуг: не добавляем товарные поля, сервисные поля выводим только если были в Excel.

4. Генерация новых объявлений — приведена к JS
   - Построение пула по задачам/локациям как в JS.
   - BasePrice flags: первые `round(count * 0.5)`.
   - Фото‑очередь по `dateLabel` → `sourceBase` → `counter`.
   - Привязка к `publicationQueue` строго по порядку.
   - AdId соответствует JS (с учётом sourceBase).

5. Формирование XML — работает, сервисы учтены
   - XML‑генератор в `feed-core/src/xml.rs`.
   - Услуги и товары разведены (RoomType/WorkDays/Address/ServiceType и т.д.).
   - SellerAddressID обязателен.

6. Сравнение с эталоном JS — OK (с игнором случайных полей)
   - `feed-cli --xml-compare <file>` сравнивает XML по структуре и обязательным полям.
   - Игнорируются случайные поля: `Title`, `Description`, `Price`, `MinSaleQuantity`, `ConcreteGrade`, `FrostResistance`, `FlakinessIndex`, `Color`.
   - Эталон: `output/ads_14.01.xml` — совпадает по сравнению в таком режиме.

7. Фото‑пайплайн
   - Rust читает готовый `photos_links_*.json` и использует его в генерации.
   - Формат маппинга совпадает с JS (используем полные имена файлов без альтернативных ключей).

## Пошаговый план полного перехода на Rust

1. Зафиксировать эталон и критерии сравнения
   - Эталонный XML: `output/ads_14.01.xml`.
   - Сравнение: структура/обязательные поля совпадают, случайные поля допускают различия.
   - Проверка через `feed-cli --xml-compare` (игнор случайных полей уже встроен).

2. Довести генерацию фото в Rust до эквивалента JS
   - Трансформации, паттерны, водяные знаки и уникальность `_1` по sourceBase+city.
   - Сравнить статистику/логи с JS на одном и том же плане.
   - После совпадения выключить JS `generate-photo-variants.js`.

3. Довести загрузку фото в Rust
   - Прогнать Rust‑upload на реальном наборе фото.
   - Проверить, что `photos_links_*.json` совпадает по структуре с JS.
   - После совпадения выключить JS `upload-photos.js`.

4. Полный прогон пайплайна на Rust
   - Excel → обновление старых → генерация новых → XML.
   - Сверить XML с эталоном и пройти все валидации.

5. Документация и переключение
   - Обновить инструкции запуска и переменные окружения.
   - Зафиксировать «кнопку запуска» только на Rust.

6. Декомиссия JS (по необходимости)
   - Оставить JS‑скрипты только как fallback на время стабилизации.
   - После успешных прогонов убрать их из основного процесса.

## Насколько можно отказаться от JS сейчас

- Уже можно: генерация XML, обновление старых, генерация новых (всё в Rust).
- Остаётся: фото‑генерация и загрузка фото.

Итого: отказ от JS возможен на ~70–80% уже сейчас; финальный переход завершится после шагов 2–3.
